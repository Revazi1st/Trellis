# Application layer rules

Depends on Domain + SharedKernel only — never Infrastructure, Persistence, EF, or ASP.NET (arch-test enforced).

- **Vertical slices**: `Features/{Feature}/{UseCase}/` holds the command/query + its handler + its FluentValidation validator, co-located (a use case whose only input is the route's id has nothing to validate and no validator: `PayInvoice`, `VoidInvoice`, `GetInvoice`).
- **Commands/queries** implement `ICommand` / `ICommand<TResponse>` / `IQuery<TResponse>` (SharedKernel). **No mediator** — endpoints inject the handler interface directly.
- **Handlers** are `internal sealed`, implement `ICommandHandler<>` / `IQueryHandler<>`, and return `Result`/`Result<T>`. They orchestrate the domain + ports; they contain no business rules (those live in the aggregate).
- **A handler never runs another use case**: share logic through the aggregate, a domain service or a port. An injected `ICommandHandler` is that command's whole pipeline, whose UnitOfWork stage commits mid-command, and an injected `IUnitOfWork` commits by hand; `ConventionTests` refuses both in any handler's constructor.
- **Validators** are `internal sealed : AbstractValidator<T>` — shape checks only (required, length, range). Semantic rules belong in domain value objects. Run automatically via the validation decorator; never call them by hand.
- **Ports** (interfaces the outside world implements) live in `Abstractions/`: `ICurrentUser`, `IEmailSender`, `IIdentityService`, `ITokenProvider`, etc.
- **Ports never commit.** A port adds to the scoped unit of work and the UnitOfWork decorator commits once per command; the only exceptions are declared single-statement atomic writes (`ExecuteUpdate`/`ExecuteDelete`, e.g. refresh-token consume) and Identity's `UserManager`, which saves itself.
- **Domain-event handlers** implement `IDomainEventHandler<TEvent>` in `Features/{Feature}/EventHandlers/` and carry a unique `[DomainEventHandlerName("feature.event.reaction")]` — the key the outbox credits them under; never change it while messages are in flight. They run at-least-once: honour the `CancellationToken`, do unit-of-work writes **before** external side effects, and never call `SaveChanges` yourself — the outbox commits your writes.
- **One aggregate per command.** A command handler changes one aggregate. What must follow in another is a reaction: an event handler that loads the other aggregate by id through its repository, calls one of its `Result` methods and returns, leaving the commit to the outbox's checkpoint. A reaction that must stand or fall with the command (the caller has to hear that it failed) belongs in the command handler instead; event handlers run after the commit, at least once. `docs/features/invoices.md` (*From a payment to its receipt*) draws the path.
- **A command that changes several aggregates** is the exception, chosen on purpose: they commit together, and a concurrent change to any of them fails the whole command. Load every participant through its repository before the first mutation (never through another use case's handler, which `ConventionTests` refuses), with tracked loads (`GetByIdAsync`; `ListAsync` and `ListPagedAsync` read `AsNoTracking`, so a change made through them is never saved). A missing participant is that aggregate's `NotFound`: never `continue` past it, or the UnitOfWork decorator commits a "successful" half of the command. Run every fallible check, then mutate; `Result.Combine` over the checks answers every validation failure at once and returns a `NotFound` or a `Conflict` on its own.
- **Event handlers report failure by throwing** (ADR-0023). `Handle` returns `Task`, so a throw is the only failure it can report, and it is the outbox's retry signal, not an expected failure leaking out as an exception (ADR-0004 holds; `SmtpEmailSender` reports a failed send the same way). A port or a method answering `Failure` or `Unavailable`: throw, and the outbox retries that handler alone, with back-off, until it dead-letters. A permanent answer (`Validation`, `NotFound`, `Conflict`, `Forbidden`): record it on an aggregate or log it, and return; retrying a refusal only fills the dead-letter queue.
- **A non-idempotent external call from a handler** (a charge, a provider's POST) carries an idempotency key built from the event's business identity and the handler's `[DomainEventHandlerName]` (`{InvoiceId}:invoices.paid.charge-card`), so the provider recognises the redelivery that at-least-once allows; a fact that can happen twice for one business id carries its own id on the event. An instant the handler needs travels on the event, from the method that already received it (`Invoice.MarkPaid(paidAtUtc)`), never from a clock read in the handler.
- **Per-record authorization** (an owner, a team) is the feature's own: a domain `OwnerId`, never the audit `CreatedBy`, enforced in the specification or repository so that a non-owner gets the aggregate's `NotFound`, and an owner-scoped read keys its cache entry by owner or skips the cache, because a hit never runs the handler. The recipe is in `docs/features/auth.md` (*Protecting an endpoint*); Invoices stay business-wide.
- **A port's errors** (`Abstractions/*Errors.cs`) take their `ErrorType` from the chooser in `domain.md`: `Unavailable` for a dependency that is down for now, `Failure` for one that refused us, which no wait cures.
- Registration is automatic (Scrutor scan + decorator pipeline in `DependencyInjection.cs`) — no manual DI lines per handler.
- **Telemetry names** (`TelemetryNamingTests`, ADR-0028): a meter or `ActivitySource` is named `Trellis.<Area>` and needs no host registration (ServiceDefaults exports `Trellis.*` everywhere); instruments are `trellis.<area>.<name>` and pass `unit:`; a custom attribute is `trellis.<area>.<name>` unless an OpenTelemetry semantic-convention name (`error.type`) carries exactly its meaning.

Decorator pipeline: Tracing → Logging → Validation → UnitOfWork → handler (queries skip UnitOfWork). Every invocation writes one span and, inside it, one outcome line in the `UseCase` scope, logged under the use case's own command or query type, so `Logging:LogLevel:<feature namespace>` sets one feature's level (ADR-0028): Information for success and for classified expected failures (a stale `If-Match`'s `ErrorType.PreconditionFailed` included), Warning for `ErrorType.Failure` and for `ErrorType.Unavailable` (a dependency is down), Error only when the use case throws; a failure line names the error type and code (a validation failure its `field:code` pairs), never the description. Handlers do not log their own outcomes.
